不用 IDE，我如何用 Codex 维护个人博客

2026年08月04日 技术 约2.4k字 预计需要8分钟

从无源码重建 Hexo，到预览、改版、整理文章和发布，我如何只通过对话与 Codex 协作维护这个博客。

过去提到“维护网站”，我首先想到的是打开 IDE，在目录树中寻找文件，再切换到终端运行命令。即使只是改一个导航名称，也要知道配置在哪里、使用什么语法，以及改完后怎样重新构建。

这次重新维护博客时，我采用了另一种方式：没有打开 IDE，而是在 Codex 中直接描述自己想要的结果。例如“隐藏下载中心和我的朋友栏目”“去掉关于页面的图片”“把这篇 Word 文档发布成文章”，或者更简单的一句“提交发布”。

Codex 负责检查项目、修改文件、运行 Hexo 和 Git 命令；我则在浏览器中观察效果，再用自然语言继续提出调整。整个过程更像我在说明意图和做设计判断，而不是亲自操作每个文件。

不用 IDE，并不等于不需要源码、版本控制和构建流程。变化的只是我与这些工具交互的方式。

起点：一个能访问，却无法继续写的博客

最初，这个网站仍然能够通过 GitHub Pages 打开，但仓库中只有已经生成的 HTML、CSS、JavaScript 和图片。原来的 Markdown、Hexo 配置、主题设置和依赖文件都不在了。

我可以看到旧网站，却不能方便地写一篇新文章。这也是我第一次明确感受到：线上网页只是构建结果，不是可以继续维护的源码。

我把 GitHub 仓库交给 Codex，要求它在本地恢复开发环境。它先检查现有文件和页面结构，判断网站使用 Hexo 与 Nexmoe 主题，然后重新建立 package.json、站点配置、主题配置、文章目录和脚手架。原站中的图片等静态资源得以保留，源码工程则重新创建。

最后，项目形成了两个职责清楚的分支：

  • source 保存 Markdown、配置、依赖和主题设置；
  • main 保存 Hexo 生成的网页，用于 GitHub Pages 发布。

这一步看似只是重建项目，实际上恢复的是“写作—预览—构建—发布”的完整能力。

我不再寻找文件，而是描述结果

源码恢复之后，我没有记住每一个配置项的位置。多数时候，我只说明希望网站变成什么样。

例如，我说“删除音乐播放器”，Codex 会先查找播放器来自主题配置、页面脚本还是第三方组件，再删除相关设置并运行构建。我要隐藏导航栏目时，它会修改主题菜单，而不是简单用 CSS 把内容遮住。我要调整首页图片时，它会同时考虑图片高度、裁剪位置和移动端显示。

这种方式与直接让 AI 生成一段代码不同。对我来说，真正有用的地方是它能够完成一整段连续工作：

  1. 阅读现有项目；
  2. 找到改动位置；
  3. 修改源码；
  4. 运行构建；
  5. 检查生成结果；
  6. 根据我的反馈继续调整。

本地预览是我们共同的“画布”

自然语言并不能一次表达所有视觉细节。很多要求只有看到页面之后才会出现。

更换首页配图时，我先觉得图片太高；调整高度后，又发现裁剪没有保留书。更换图标时，我先要求透明背景，随后又觉得图形本身不好看。整理书单时，状态标签虽然出现了，却没有与其他书的状态对齐。

这些都不是一开始能够写进完整需求的问题。我的做法是让 Codex 保持本地 Hexo 服务运行，然后在浏览器中查看 http://127.0.0.1:4000：

我负责指出“哪里看起来不对”，Codex 负责定位对应的 HTML、CSS 或配置。修改后再构建，并通过桌面与手机尺寸检查长书名、卡片高度和状态对齐。

因此，本地预览不是开发结束后的验收步骤，而是对话的一部分。页面本身就是最准确的反馈。

Codex 维护的不只是代码

这个博客的内容并不总是从 Markdown 开始。《重拾阅读》最初是一份 Word 文档，里面有正文、灰色说明文字、署名和日期。我把文档交给 Codex，让它区分正文与非正文，再转换为适合博客的结构。

之后的调整仍然通过对话完成：署名右对齐、日期右对齐、引用文字使用楷体、保留引号但不能遮挡正文、段落首行缩进两个字。Codex 不只是把文字复制到网页，而是根据文档语义和页面效果反复整理。

“书与山”页面也是如此。我提供一份书单文档，再陆续告诉它哪些书已读、在读、值得推荐。Codex 重新分类书目、计算状态数量、设计标签，并在每次新增书目后重新检查排版。为了让这条约定以后仍然有效，我们还把它写进项目的 AGENTS.md。

这让我意识到，维护个人博客不只是写代码，也包括处理文档、组织内容、调整视觉和建立长期规则。Codex 的技能机制正适合承载这类可重复流程。

“提交发布”仍然是一条明确边界

最初，我经常把“修改”和“发布”看作同一个动作。后来我发现，如果每次调整都立即推送，出现不满意的效果时就不容易回退。

现在我们的默认流程是：先只修改本地，等我在浏览器中确认后，再明确说“提交发布”。Codex 随后会检查 Git 差异、只暂存本次相关文件、创建独立提交，先推送 source，再让 Hexo 部署到 main。

Git 仍然是整个协作中最重要的安全网。Codex 界面中的撤销能力不能代替提交记录，已经发布的内容也应该通过新的反向提交恢复，而不是直接改写远端历史。

每一项修改单独提交，还有另一个好处：换到另一台电脑时，只要拉取 source 分支，就能继续维护，不需要依赖当前这段对话或某台电脑上的临时文件。

我仍然需要做什么

不用 IDE 之后，我没有退出维护过程，只是把注意力从语法和文件路径转向了判断。

我仍然需要决定网站要保留什么、哪些信息不愿公开、文章应该使用什么语气，以及一个页面究竟好不好看。Codex 可以提出分类方案，但书是否读过、是否值得推荐，只有我知道。它可以生成图片和布局，但我仍然要指出书被裁掉了、图标不好看，或者某段文字不属于正文。

我还需要保留几个基本习惯：

  • 修改前确认 Git 工作区状态；
  • 发布前查看本地页面；
  • 不在 main 上直接编辑生成文件；
  • 换电脑前先推送 source；
  • 对删除、覆盖和发布保持明确授权；
  • 不把个人隐私因为“方便”而暴露在网站上。

Codex 降低了操作门槛，但没有替我承担最终判断。它更像一个能够执行、检查并解释的协作者，而不是自动决定网站方向的人。

从“我不会改”到“我想这样改”

以前面对网站问题，我常常先问：“这个文件在哪里？”“这段 CSS 应该怎么写？”现在我更习惯先说：“我希望它看起来怎样？”

这种变化并没有让技术消失。Hexo、Node.js、Git、Markdown 和 GitHub Pages 仍然在后台工作，只是 Codex 把它们连接成了一个可以用语言驱动的流程。我不需要每天使用 IDE，却仍然拥有源码、构建、测试和版本记录。

这个博客也因此从一个已经发布但难以继续修改的静态网站，变成了可以持续整理的个人空间。文章、书单、图片、导航和页尾，都是在一次次“先试试看”“这里不太对”“再改一点”的对话中逐渐形成的。

而你现在读到的这篇文章，也同样是这样完成的：我先提出一个想法，Codex 根据真实的维护记录整理成稿，再由我决定它是否应该出现在网站上。
